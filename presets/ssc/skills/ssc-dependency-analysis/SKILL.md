# 依赖与组件安全分析

依据用户任务区分源码仓库、安装目录和发布产物；信息足够时直接开展范围内的只读审查。不为扫描擅自安装依赖、执行项目脚本、修改项目或扩大到工作区外的全局环境。

## 源码依赖审查

用户已指定受支持的锁文件或声明文件时，可直接调用 `dependency_audit`；否则先用 `dependency_targets` 定位来源。按任务范围处理 `lockfileCandidates` 中标为 `implemented` 的来源及所需的 `manifestAuditCandidates`，由审计工具负责调用 Syft。多个锁文件不要无依据地只选一个，也不要推断根锁文件必然覆盖全部子项目。

完成前，任务范围内每个发现的候选应有审计结果或明确的未扫描原因。详细 `targets` 截断不等于候选清单截断；检查候选完整性和诊断。发现不完整时，在任务范围内缩小 `root` 继续定位，无法补齐则报告缺口，不宣称全仓覆盖。仅有声明而没有可审计来源的部分也应说明。

OSV 查询默认向公开服务发送包名、生态与版本；仅生成 SBOM、离线审查或用户不允许外发时，设置 `query_vulnerabilities: false`。按工具状态和诊断报告查询失败、跳过、无生态映射或结果截断，不能将其解释为零漏洞。

## 风险判断与交付

锁文件记录、声明清单和安装元数据是不同证据，均不自动证明最终交付内容。OSV 命中是公告候选，不等于项目可利用；本地包同名同版本也不证明它就是注册表中的发布包。需要判断项目影响时，围绕重要候选检查依赖用途、引入关系及受影响功能，给出可核查依据；未核实的部分保留为待确认。

报告按来源说明审查结果，并提供对应 SBOM 路径；区分组件清点、公告候选、已核实影响和覆盖缺口。不必复述所有工具字段，不把不同来源的数量直接相加当作唯一组件数，也不把版本或清单差异直接判定为漏洞。

## 可选：已有 npm 安装目录

任务涉及实际安装内容且工作区内已有对应目录时，可用 `installed_npm_audit` 补充检查。它只读取物理包清单，跳过符号链接，不验证包文件完整性或运行时加载；不能据此声称完整覆盖 pnpm 链接布局、其他生态或部署产物。按返回结果说明跳过、截断和身份识别限制，不将物理清单数与去重后的组件数混用。源码依赖审查无需为了这一步安装依赖。
