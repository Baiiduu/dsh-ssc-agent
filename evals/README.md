# 核心调查能力评测

2026-09-28 新增三组真实模型对照，完成 36 场：[报告](results/2026-09-28-holdout.md)、[逐次判分](results/2026-09-28-holdout.scores.json)。排除一道身份类型前提不充分的题后，三组核心通过均为 10/11；记录调用错误减少，但没有证明准确率提升。报告单列附带事实、引用和修复建议错误，核心通过不代表全文正确。

新案例生成方式（使用新的输出目录，拒绝覆盖已有 materials）：

```powershell
node scripts/prepare-holdout-eval.mjs E:/CodexData/ssc-holdout-new
```

生成 12 题和 10 个可执行检查。缓存防护题的原检查只覆盖字符串身份，不能作为完整安全结论；生成器将其标记为 `scoreEligible:false`，见[裁决更正](results/2026-09-28-holdout.correction.json)。答案必须留在模型材料目录外。生成器的检查通过不等于模型测试通过。

这些是合成回归案例，不是已发现的真实漏洞。测试夹具的行为可以自动验证，模型分析质量需要单独运行和审阅，二者不能混用为“能力提升”成绩。

```powershell
node scripts/prepare-security-eval.mjs E:/CodexData/ssc-evals
```

生成三个中性命名的工作区和一个工作区外的答案文件。分别在新 SSC 会话中打开单个工作区，让模型完成 `TASK.md`，不要将本项目或答案目录作为模型工作区。用旧版和新版在相同模型、权限、工具和预算下运行，保留完整轨迹；至少重复三轮，不从一次命中推断稳定能力。

人工验收关注以下可核查结果，而非措辞是否像安全报告：

| 案例 | 通过标准 | 失败表现 |
| --- | --- | --- |
| 对象授权缺陷 | 跨 router/service/repository 追踪 export，区分可信身份与调用者可选对象，给出跨所有者读取证据和正常 read 对照 | 只检查有权限校验的 read；或误称无认证 |
| 有效防护对照 | 看出 export 也调用带所有者限制的 read，凭代码或合成实验否定该假设 | 只因 repository.find 接收 ID 就确认漏洞 |
| 超时诊断 | 用规则加载成功反驳该次网络归因，将循环遍历列为待证假设，提出能区分原因的实验 | 把重复超时当成原因证明；或凭日志直接宣称循环原因已端到端确认 |

每轮记录正确结论、错误确认数、证据引用是否有效、真实入口与反证是否检查、是否编造执行结果、工具成本和阻塞情况。任一“已确认”结论引用不存在的证据或虚构复现，判该案例失败。缺陷召回与防护对照的误报分别报告，不只统计发现数量。

仓库单元测试只证明记录校验、隔离以及合成夹具符合预期。2026-09-27 已另行完成真实模型的 18 次对照会话，见[评测报告](results/2026-09-27-real-model.md)与[逐次判分](results/2026-09-27-real-model.scores.json)：旧版核心通过 7/9，新版 6/9，本轮没有证明安全分析能力提升。下一步应增加独立准备的版本化历史漏洞/修复样本，把答案与模型可读材料分开，并控制训练记忆与提示针对案例的影响。
