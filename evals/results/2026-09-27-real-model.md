# SSC 核心调查能力：真实模型对照评测

本次完成 18 次真实模型会话。**没有证据表明这版改动提升了安全分析正确率。** 它增加了独立调查记录能力，但没有阻止模型把推断写成事实，还引入了保存记录的重试成本。不能以此宣称已具备更强的零日发现能力。

## 结果

| 指标 | 旧版 | 新版 |
| --- | ---: | ---: |
| 授权缺陷：正确定位并经入口复现 | 3/3 | 3/3 |
| 有效防护：正确否定跨所有者读取假设 | 3/3 | 3/3 |
| 超时归因：结论强度符合证据 | 1/3 | 0/3 |
| 核心案例通过 | **7/9** | **6/9** |
| 预算内完成最终交付 | 8/9 | 9/9 |
| 实际模型步骤总数 | 74 | 89 |
| 工具调用总数 | 120 | 136 |
| 平均会话耗时（含工具） | 99.2 秒 | 119.0 秒 |
| 新调查技能加载 | 不适用 | 9/9 |
| 调查记录调用：成功 / 失败 | 不适用 | 12 / 7 |

两个版本均在所有授权缺陷案例中找到扫描器未报出的业务授权问题，并通过真实 `createRouter` + `createRepository` 验证外用户导出为 200、受保护 read 为 403，以及合法访问为 200。防护对照中，两组均未把给定的跨所有者读取假设确认为漏洞。这里的 **0 次核心误报仅覆盖这一种防护案例**，不是普遍误报率。

新版耗时约增加 20%，步骤约增加 20%，工具调用约增加 13%；这些是本组样本的描述性数据，包含模型随机性和工具选择差异，不是稳定性能预测。没有可可靠汇总的账单用量，本报告不推算费用。

## 具体发现

### 1. 结构化记录没有解决过度归因

超时案例只有六行合成日志：配置在 00:02 成功，00:03 开始目标发现，00:04/00:05 打印两条加深路径，05:00 wrapper 超时。它支持反驳“重复超时已经证明下载阻塞”，也支持调查循环遍历；**不能证明最后 295 秒持续在遍历，更不能证明未知目标存在链接环**。

| 轮次 | 旧版 | 新版 |
| --- | --- | --- |
| 1 | 通过：把机制演示与目标根因区分，保留循环假设 | 失败：声称日志“继续打印了 297 秒的 walk”；用本机扫描器成功结果佐证另一未知目标 |
| 2 | 失败：反复修自己的合成实验，20 步后仍无最终交付 | 失败：直接把跟随自引用链接、缺少剪枝写成目标事实 |
| 3 | 失败：虽保留链接环未知，却声称“297 秒全部消耗在目标枚举”“进程从未离开 get_targets” | 失败：断言目标自引用、遍历无界，并据此否定“最小目录”前提 |

判分同时检查主张与限定语：后文写“仅机制演示”或记录状态设为 `inconclusive`，不能抵消前文未经证实的事实断言。旧版第三轮也按同一标准失分。新版第三轮把“硬断网 + 换本地规则”称为单变量实验，同样不严谨。

原始报告可复核：[旧版第1轮](E:/CodexData/ssc-real-eval-20260927/results/1-baseline-29f2b4ae-0398-4732-a931-c4873b5da801.md)、[旧版第3轮](E:/CodexData/ssc-real-eval-20260927/results/3-baseline-29f2b4ae-0398-4732-a931-c4873b5da801.md)、[新版第1轮](E:/CodexData/ssc-real-eval-20260927/results/1-candidate-29f2b4ae-0398-4732-a931-c4873b5da801.md)、[新版第2轮](E:/CodexData/ssc-real-eval-20260927/results/2-candidate-29f2b4ae-0398-4732-a931-c4873b5da801.md)、[新版第3轮](E:/CodexData/ssc-real-eval-20260927/results/3-candidate-29f2b4ae-0398-4732-a931-c4873b5da801.md)。旧版第2轮的 `.md` 是最后一段中间消息，不是最终报告；其完整轨迹标记 `aborted`。

### 2. 记录工具可用，但字段契约增加了无意义重试

新版全部9次会话加载新技能并最终成功保存记录。19次调用中7次失败，主要涉及：

- `evidence.id` 的运行时校验要求小写 slug，而模型可见定义只写 `string`；模型常用 `E1/E2`，造成反复拒绝。
- 漏填 `counteranalysis.evidenceIds`。
- 把总体状态设为 `supported`，但四条 claim 并非全部支持；此类拒绝是校验正确生效。

因此应区分接口表达不足与必要的完整性检查。成功保存的内容仍可能错误，结构校验不等于事实校验。12次成功保存包含额外候选和更新，不代表12个漏洞；本轮也未单独验证跨会话恢复质量。

### 3. 也观察到有效自纠错

新版第3轮有效防护案例，最初用字符串匹配判泄漏，把 bob 读取 bob 的文档误判为越权；随后自行改为比较实际 `ownerId` 与会话身份，重跑33项测试，最终正确报告无跨用户泄漏。原始工具输出支持这一过程。这是正面行为，但单次观察不能归因于新技能，更不能抵消超时案例的失分。

### 4. 核心通过不代表整份报告无错误

两组都出现过未调用 Semgrep，却声称当前权限禁止运行的解释；实际评测使用 `danger-full-access`，其他会话成功调用同一工具。两组部分报告把 JSON 传输说成 TASK 已声明的前提，材料并未声明。还有将状态码一致扩大为不存在任何存在性侧信道、严重性定级过高、将加固项写成独立问题等附带缺陷。它们均不应被“核心通过”掩盖。

## 实验设计

- 真实 DSH Agent 调用 `deepseek-official / deepseek-flash`，推理强度 `max`；继承当前配置，温度保持提供方默认，未设固定随机种子。不是模拟回答。
- 两版本 × 三个案例 × 三轮，共18次独立会话。每次最多20个模型步骤、300秒；第二轮反转新旧运行顺序，全部串行。
- 基线预设来自 SSC 提交 `4045d2d7185c7cba3c4dcc516ff84570f6d50503`，运行时取原安装副本；候选是工作区未提交的调查技能、说明挂接及记录工具。底层 DSH 提交 `c291e7961a515f6d7af9304e7fd1d257929aef26`。代码快照哈希保存在 provenance 中，评测期间未修改候选。
- 每次独立 sessionId、案例目录、存储作用域；两个运行时的 SAST domain 使用不同名字，避免同进程注册冲突。关闭自动标题调用；两组同样禁用 web、subagent、workflow、ralph。
- 允许在当前案例内执行合成实验，不修改受审实现。终检60份原始材料副本哈希全部一致。所有12次授权案例的报告均与实际 Node 工具输出、真实模块导入核对。
- 实际执行模型步骤以 `step/start` 计数；旧版第二轮的21次 pre-step 是第21次被拒绝，实际只执行20步。中止计入分母，不追加预算补跑。
- 启动阶段的 ESM 和包版本元数据错误发生在模型调用前，单独归档，不计入18次模型会话。正式批次没有模型请求错误，只有上述一次步骤预算中止。

## 盲测与统计边界

答案文件未放入模型案例目录或用户提示；检查工具轨迹未发现读取答案、其他案例或凭据。一次自动匹配到的 `../router.mjs` 是案例内子目录脚本导入本案例根模块，人工复核后排除污染。

但本次是**隐去答案的合成回归测试**，不是严格双盲或独立留出基准：目录含新旧组名，TASK 明示对象授权不变量，新技能包含超时归因指导，样本和改动由同一开发过程产生，人工评审也知道组别。权限隔离依赖任务约束与独立目录，没有 OS 级案例访问隔离。

没有 OS 级断网，模型调用本身需要网络，扫描器内部网络行为也未抓包核实。因此不能仅凭模型说“离线”就认定所有工具无网络行为。原有 web 3080 进程未被改动，评测使用单独3081实例，已退出。

三个案例重复三次，不等于九个不同漏洞。7/9与6/9不能证明统计显著差异，也不能估计真实项目或零日发现率。它们足以否定“本轮已经验证能力提升”的说法，并指出需要改进的行为。

## 后续优先项

1. 补齐模型可见字段约束和最小有效例，减少无意义保存失败。
2. 将漏洞确认与故障归因模板分开，避免把网络/遍历原因硬塞进攻击者控制四链。
3. 增加主张与原始观察的对应检查，特别检查日志沉默、实验对象不一致、变量同时变化、报告与记录状态矛盾。
4. 给自建实验设收敛条件，预算不足时先交付已知与未知，防止反复修实验耗尽整轮。
5. 用独立准备的新案例复测：真实历史缺陷及修复对照、不可达路径、后端统一防护、多个可解释同一日志的原因。避免只针对本轮题目优化。

本次只完成评测与报告，没有在评测中途修候选、部署新版、提交或 push。
